## What this file is

This is a **global gitignore** file, applied to every Git repository on the machine via the `core.excludesFile` setting in `~/.gitconfig`. Unlike a per-repo `.gitignore` that only affects one project, this file tells Git to ignore matching files everywhere.

## Required Setup

> **This is handled automatically.** The script `run_once_after_configure-git-global.sh` runs on `chezmoi apply` and sets `core.excludesFile` in your global Git config.
>
> If you need to do it manually, add the following to your `~/.gitconfig`:
>
> ```gitconfig
> [core]
>     excludesfile = ~/.gitignore_global
> ```
>
> Without this setting, Git will not read the global ignore rules and all patterns in this file will be silently ignored.

## Why a global gitignore instead of per-repo

Machine-specific artifacts -- macOS metadata, IDE project directories, AI tool caches -- are generated by the local environment, not by the project itself. Listing them in every repository's `.gitignore` is noise that other contributors shouldn't have to maintain. A single global file keeps all repos clean without polluting their ignore rules with things like `.DS_Store` or `.idea/`.

## Sections

### macOS system files

Finder and the filesystem generate invisible metadata that has no purpose inside a repository. These are ignored globally because they appear in every directory on macOS regardless of what the project is.

Examples: `.DS_Store`, `._*` (resource forks / thumbnails), `.Spotlight-V100`, `.Trashes`

### JetBrains IDEs

PhpStorm, WebStorm, IntelliJ, and other JetBrains products write `.idea/` directories, `.iml` module files, and local workspace state. These are user-specific and machine-specific -- they contain paths, window layouts, and local data-source credentials that differ per developer.

Examples: `.idea/`, `*.iml`, `.idea/workspace.xml`

### VS Code / VSCodium

VS Code stores user settings, debug configs, and extension state in `.vscode/`. Workspace files and extension test/cache directories are also generated locally. None of this belongs in version control since each developer configures their editor differently.

Examples: `.vscode/`, `*.code-workspace`, `.vscode-test/`

### AI / assistant tools

AI-powered editors and completion tools (Cursor, Sourcegraph Cody, Codeium, TabNine, GitHub Copilot) each create their own config and cache directories. These change frequently, are machine-local, and can contain auth tokens or telemetry data.

Examples: `.cursor/`, `.tabnine/`, `.github-copilot/`

### Claude

Claude Code and related tooling generate project-level config (`CLAUDE.md`, `.claude/`), caches, logs, and workspace directories. These are specific to the local development workflow and should not leak into shared repositories.

Examples: `.claude/`, `claude-cache/`, `.claude-workspace/`

### Other

A catch-all section for environment files, local service configs, and workflow artifacts. `.envrc` (direnv) and `.env.*` files often contain secrets. The `valet/` directory is from Laravel Valet. `.devwork/` holds task records for the local workflow system.

The file explicitly un-ignores `.env.example` and `.env.*.example` so that template env files still get committed.

Examples: `.envrc`, `.env.*`, `.devwork/`, `!.env.example`
